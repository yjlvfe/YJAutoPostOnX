## 💾 معمارية التخزين في SQLite (`sqliteStore.js`)

تعتمد إدارة البيانات في البوت على مكتبة Node.js الرسمية المدمجة حديثاً `node:sqlite` عبر صنف `DatabaseSync`.
يتم إنشاء قاعدة البيانات بملف واحد في المسار `Bot/data/state.sqlite`، مع ضبط الخصائص التالية عند الفتح:

```sql
PRAGMA busy_timeout = 30000;
PRAGMA journal_mode = WAL;
PRAGMA synchronous = FULL;
PRAGMA user_version = 1;
```

## ⚠️ الخلل المعماري: جدول JSON أحادي السطر (Single-Row Blob Anti-Pattern)

تم تصميم بنية الجدول في `src/sqliteStore.js:101` كما يلي:

```sql
CREATE TABLE state (
  id INTEGER PRIMARY KEY CHECK (id = 1),
  json TEXT NOT NULL,
  revision INTEGER NOT NULL CHECK (revision >= 0)
);
```

### تحليل الأثر الهندسي والأداء
1. **انعدام الفهرسة والعلاقات (Zero Schema Normalization):**
   - يحتوي الحقل النصي `json` على **شجرة بيانات التطبيق كاملة**:
     - مصفوفة عناصر الطابور `items: [...]` (قد تحتوي على مئات المنشورات).
     - مصفوفة الحسابات `accounts: [...]` مع كافة بياناتها وإعداداتها.
     - سجلات الكوتا اليومية لكل حساب `posting.quota: {...}`.
     - مؤشرات التوقيت والجدولة `posting.publishingAt` و `posting.nextPostAt`.
     - إعدادات البوت العامة `settings: {...}`.
2. **تضخم عمليات الكتابة (Extreme Write Amplification):**
   - عندما يحتاج النظام لتعديل حرف واحد (مثل تحديث حالة منشور من `pending` إلى `processing`)، يضطر المحرك إلى:
     1. قراءة النص الكامل من القرص.
     2. عمل `JSON.parse` للشجرة بأكملها داخل الذاكرة.
     3. نسخ الكائن بعمق `structuredClone`.
     4. تعديل الحقل المطلوب.
     5. عمل `JSON.stringify` للشجرة بأكملها.
     6. كتابة مئات الكيلوبايتات (أو الميجابايتات مع كبر السجل) إلى ملف WAL على القرص.
     7. تنفيذ عملية مزامنة قسرية `fsync` للقرص بسبب `PRAGMA synchronous = FULL`.
3. **اختناق التزامن وتجميد الخيط الرئيسي:**
   - كافة المعاملات تستخدم `BEGIN IMMEDIATE`، مما يقفل قاعدة البيانات بالكامل أمام أي كتابات أخرى.
   - إذا كان هناك طلب طويل جاري (مثل استيراد ملف حسابات أو تحديث كبير)، تتوقف عمليات حجز الطابور وتتعطل واجهة تيليجرام حتى انتهاء المعاملة.

## 🔄 آلة حالات المنشور (Item State Machine)

يتحرك المنشور في طابور النشر عبر الحالات التالية بدقة:

```
                  ┌───────────────┐
                  │    pending    │ ◄────────────────────────┐
                  └───────┬───────┘                          │
                          │ حجز الدورة (claimCycleItem)       │
                          ▼                                  │
                  ┌───────────────┐                          │ تعافي آمن قبل الإرسال
                  │   processing  │ (مع رمز attempt.token)   │ (R_BEFORE_POST)
                  └───────┬───────┘                          │
                          │ مصافحة النشر (onDispatch)        │
                          ▼                                  │
                  ┌───────────────┐                          │
                  │  dispatching  │                          │
                  └───────┬───────┘                          │
                          │ استلام نتيجة النشر                │
             ┌────────────┼─────────────┐                    │
             │            │             │                    │
             ▼            ▼             ▼                    │
     ┌───────────┐ ┌─────────────┐ ┌───────────┐             │
     │ published │ │  ambiguous  │ │ cancelled │             │
     └───────────┘ └─────────────┘ └───────────┘             │
           │              ▲                                  │
           │              └──────────────────────────────────┘
           │                فشل بعد الإرسال أو انقطاع غير مؤكد
           ▼
     [استهلاك الكوتا]
```

### توصيف الحالات:
- **`pending`:** منشور في الطابور بانتظار موعد النشر وحساب متاح.
- **`processing` (أو `claimed`):** تم حجز المنشور في الدورة الحالية وتوليد رمز `attempt.token` فريد (UUID) لحمايته من الحجز المزدوج.
- **`dispatching`:** تم تأكيد بدء الإرسال عبر جسر بايثون؛ أصبحت محاولة النشر جارية ولا يجوز التراجع عنها تلقائياً.
- **`published`:** تم تأكيد النشر رسمياً برقم التغريدة ورابطها من GraphQL. في نفس المعاملة الذرية تُستهلك كوتا الحساب ويُسجل موعد النشر القادم.
- **`ambiguous`:** حالة غير مؤكدة (حدث انقطاع شبكي أو مهلة انتظار بعد بدء الإرسال). يُعزل المنشور تماماً ولا يُعاد إرساله آلياً لحماية الحساب من التكرار.
- **`cancelled`:** منشور ملغى لتجاوز الحد الأقصى لعدد الحروف أو مخالفة الشروط.

## ⏰ نظام الكوتا وحسابات منتصف الليل بتوقيت الرياض (`riyadhDay`)

تُحسب الكوتا اليومية لكل حساب بناءً على التاريخ الرسمي في المملكة العربية السعودية (`Asia/Riyadh` UTC+03:00):

```javascript
// src/quota.js و src/runner.js:593
function riyadhDay(date = new Date()) {
  const parts = new Intl.DateTimeFormat('en-CA', {
    timeZone: 'Asia/Riyadh', year: 'numeric', month: '2-digit', day: '2-digit'
  }).formatToParts(date);
  return `${parts.find(p=>p.type==='year').value}-${parts.find(p=>p.type==='month').value}-${parts.find(p=>p.type==='day').value}`;
}
```

### الذرية بين تأكيد النشر واستهلاك الكوتا:
في `src/runner.js:589-596`:
يتم تسجيل `i.state = 'published'` وزيادة `s.posting.quota[day][accountId] += 1` **داخل نفس معاملة SQLite الذرية**.
أثبت الاختبار `R_PERSISTED` أنه لا يمكن للنظام أن يسجل منشوراً ناجحاً دون تسجيل كوتا، أو يسجل كوتا دون نجاح المنشور.

### لغز "التعليق عند 9":
كشفت التحقيقات السابقة أن عرض اللوحة للرقم "9" لم يكن عطلاً في عداد الكوتا نفسه، بل كان بسبب بلوغ الحساب الحد الأقصى المحدد في الإعدادات (مثلاً 9 أو 10 منشورات يومياً). وعندما تبلغ الكوتا حدها الأقصى، يمتنع `claimCycleItem` عن اختيار الحساب حتى حلول الساعة 00:00 بتوقيت الرياض، فيبدو الحساب في لوحة التحكم وكأنه متوقف عند الرقم 9.

## 🧪 نتائج اختبارات الطابور وقاعدة البيانات المعزولة (Suites Q & R)

تم إجراء 9 اختبارات مكثفة لمعمارية الطابور والتعافي:

| رمز الاختبار | السيناريو وظروف التشغيل | السلوك المرصود | النتيجة الهندسية |
|---|---|---|---|
| **`Q_RACE`** | 5 عمليات تتنافس على حجز عنصر واحد بالتوازي | عملية واحدة فقط فازت بالحجز، و4 عمليات تم رفضها | **PASS:** منع كامل للحجز المزدوج |
| **`Q_BUSY`** | عملية حاولت القفل أثناء قفل معلق لمدة 0.3 ثانية | انتظرت العملية انتهاء القفل وأنجزت الحجز بنجاح | **PASS:** نجاح مهلة busy_timeout |
| **`Q_CRASH_TX`** | انهيار العملية أثناء معاملة كتابة مفتوحة | ألغى SQLite المعاملة (Rollback) واستمرت سلامة الملف | **PASS:** الذرية متحققة في SQLite |
| **`Q_STALE`** | تعافي النظام بعد انهيار سابق قبل الإرسال | استرجاع المنشور برمز محاولة جديد وغير مكرر | **PASS:** تجديد الرموز عند التعافي |
| **`Q_LATE_CALLBACK`** | وصول استجابة قديمة مع وجود رمز محاولة جديد | رفضت العملية الإرسال، لكنها مسحت المحاولة الجديدة وحولتها إلى ambiguous | **FAIL (المشكلة مثبتة):** غياب فحص مطابقة رمز المحاولة |
| **`R_BEFORE_POST`** | إيقاف العملية بالقوة قبل بدء الإرسال ثم استئنافها | استعاد المنظم العنصر بأمان ونشره مرة واحدة فقط | **PASS:** تعافي آمن قبل خروج الطلب |
| **`R_ACCEPTED`** | إيقاف العملية بعد استلام الخادم للطلب | تحول العنصر إلى `ambiguous` ومُنعت إعادة الإرسال | **PASS:** سياج أمان الغموض فعال |
| **`R_RESPONSE`** | إيقاف العملية بعد صدور الرد وقبل تسليمه | تحول العنصر إلى `ambiguous` ومُنعت إعادة الإرسال | **PASS:** سياج أمان الغموض فعال |
| **`R_PERSISTED`** | فحص الحالة بعد اكتمال المعاملة | استقرار النشر والكوتا دون أي طلبات مكررة | **PASS:** ذرية النشر والكوتا متحققة |

## 🛠️ التوصيات المعمارية لإصلاح قاعدة البيانات
1. **تفكيك الجدول الأحادي إلى جداول علائقية حقيقية:**
   - جدول `items` للمنشورات وفهرسة حقل `state` و `scheduled_at`.
   - جدول `accounts` للحسابات وحالاتها وإعداداتها.
   - جدول `daily_quotas` لإدارة الكوتا برقم السطر وليس داخل نص عملاق.
2. **فرض سياج رمز المحاولة (Attempt Token Fencing):**
   - تعديل استعلام التحديث ليشمل شرط `WHERE id = ? AND attempt_token = ?`.
