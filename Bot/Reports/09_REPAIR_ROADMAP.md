## 🗺️ الترتيب المتسلسل لمراحل الإصلاح (Phased Execution Roadmap)

تم ترتيب مراحل الإصلاح وفقاً للأثر على استقرار النظام وحماية الحسابات من النشر المكرر، بدءاً من المشاكل الحرجة P0 وانتهاءً بالتحسينات المعمارية:

```
┌────────────────────────────────────────────────────────┐
│ Phase 1: سياج النشر وحماية الحسابات من التكرار (P0)      │
│ (إلغاء Fallback في بايثون + إلغاء إعادة تدوير التايملاين) │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ Phase 2: توحيد الخدمات وإدارة أقفال تيليجرام (P0)       │
│ (إلغاء خدمة المستخدم + حماية القفل + ضبط المهل)         │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ Phase 3: حماية التزامن وإصلاح مستودع SQLite (P1)        │
│ (فرض سياج attempt.token + تفكيك جدول JSON الأحادي)      │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ Phase 4: تأمين الحسابات وشبكة البروكسي (P1 / P2)        │
│ (تشفير الكوكيز + إلغاء تجاوز use_cache + تصحيح الأخطاء) │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ Phase 5: تحسين أداء محرك المحتوى والأتمتة (P1 / P2)     │
│ (نقل المعالجة الدلالية لـ Worker Thread + ضبط التوكنات) │
└────────────────────────────────────────────────────────┘
```

## 🛠️ تفاصيل مراحل الإصلاح

### المرحلة 1: سياج النشر وحماية الحسابات من التكرار (Publishing Safety Fence)
- **الأولوية:** P0 (حرجة جداً — تمنع تكرار التغريدات فوراً).
- **الملفات المتأثرة:**
  - `Bot/python/direct_x_bridge.py`
  - `Bot/src/directX.js`
  - `Bot/src/runner.js`
- **التعديلات الهندسية المطلوبة:**
  1. في `OnlySocksTransport.handle_async_request`:
     - إزالة السقوط البديل التلقائي إلى `httpx` لأي طلب `POST` بعد بدء إرسال البيانات.
     - حصر استخدام البديل فقط في حالة فشل الاتصال الشبكي المسبق المؤكد قطيعاً قبل خروج أي بايتات (`Pre-send Connect Refused`).
  2. في `verify_timeline`:
     - إلغاء إرجاع `verifiedNotPosted: True` لأي طلب نشر حديث تم الشروع في إرساله.
     - استبدال مطابقة الـ 40 حرفاً الأولى بمطابقة النص الكامل أو بصمة SHA-256 للنص المنظف.
     - دعم تصفح الصفحات المتعددة (Cursors) وزيادة فترات الانتظار لتلائم الانتشار البطيء لمنصة X.
  3. في `runner.js`:
     - حذف منطق إعادة المحاولة المبني على `verifiedNotPosted`.
     - استقرار أي منشور غير مؤكد في حالة `ambiguous` دائمياً وإشعار المشرف.
- **خطة التراجع (Rollback):** الاحتفاظ بنسخة احتياطية لملفي `runner.js` و `direct_x_bridge.py` واسترجاعهما في حال تعطل تدفق النشر الطبيعي.
- **معايير قبول المرحلة (Acceptance Criteria):**
  - اجتياز اختباري `A_ACCEPT_DROP` و `A_DELAY` بحيث لا يستلم خادم الاختبار أكثر من طلب POST واحد.
  - اجتياز اختباري `B_LOST_EMPTY` و `B_RUNNER_REPLAY_ONLY` بحيث يستقر المنشور غير المؤكد في حالة `ambiguous` دون إعادة إرسال.

### المرحلة 2: توحيد الخدمات وإدارة أقفال تيليجرام (Services & Lock Unification)
- **الأولوية:** P0 (تمنع تكرار خطأ 409 وتعطل البوت).
- **الملفات المتأثرة:**
  - `/etc/systemd/system/yj-telegram-bot.service`
  - `systemd/yj-telegram-bot.user.service`
  - `Bot/src/telegramApi.js`
  - `Bot/src/watchdog.js`
- **التعديلات الهندسية المطلوبة:**
  1. تعطيل وإزالة وحدة المستخدم نهائياً:
     - `systemctl --user stop yj-telegram-bot.service`
     - `systemctl --user disable yj-telegram-bot.service`
  2. في ملف خدمة النظام `/etc/systemd/system/yj-telegram-bot.service`:
     - حذف سطور `rm -f .../telegram-runner.lock` من `ExecStartPre` و `ExecStopPost`.
  3. في كود إدارة القفل بـ Node.js:
     - تسجيل معرّف العملية (PID) ووقت البدء داخل ملف القفل، والتحقق عبر `kill -0 PID` قبل اعتبار أي قفل مهجوراً.
  4. في `telegramApi.js`:
     - ضبط مهلة قراءة مقبس تيليجرام لتكون 65 ثانية عند استخدام مهلة استطلاع 50 ثانية لمنع أخطاء `TELEGRAM_TIMEOUT`.
- **معايير قبول المرحلة:**
  - تشغيل متزامن تجريبي يؤكد رفض إقلاع النسخة الثانية فوراً وظهور رسالة القفل المشغول.
  - انعدام تام لأخطاء 409 في سجلات البوت على مدى 24 ساعة تشغيل.

### المرحلة 3: حماية التزامن وإصلاح مستودع SQLite (Concurrency & Database Hardening)
- **الأولوية:** P1 (حماية تكامل البيانات ومنع التعليق).
- **الملفات المتأثرة:**
  - `Bot/src/runner.js`
  - `Bot/src/sqliteStore.js`
  - `Bot/data/state.sqlite`
- **التعديلات الهندسية المطلوبة:**
  1. في `runner.js`:
     - فرض سياج رمز المحاولة الذري: تعديل دالة تحديث الحالة للتحقق من مطابقة `attempt.token` الحالي قبل مسح المحاولة أو كتابة الحالة، لمنع الاستجابات المتأخرة من تخريب الحالات الأحدث.
  2. في `sqliteStore.js`:
     - تحويل قاعدة البيانات من نموذج الجدول الأحادي (Single JSON Blob) إلى جداول علائقية مهيكلة (`items`, `accounts`, `quotas`, `settings`).
     - تحديث الأسطر الفردية مباشرة لخفض استهلاك الذاكرة وتفادي قفل قاعدة البيانات بالكامل.
- **معايير قبول المرحلة:**
  - اجتياز اختبار `Q_LATE_CALLBACK` برفض الاستجابة القديمة والحفاظ على الرمز الأحدث.
  - ثبات زمن تحديث حالة العنصر تحت 10 مللي ثانية مع انخفاض عمليات الكتابة في القرص بأكثر من 80%.

### المرحلة 4: تأمين الحسابات وشبكة البروكسي (Account Security & Proxy Network)
- **الأولوية:** P1 / P2 (حماية البيانات السرية ومنع تسريب IP).
- **الملفات المتأثرة:**
  - `Bot/src/accounts.js`
  - `Bot/src/directX.js`
  - `Bot/src/dockerVpn.js`
  - `Bot/python/direct_x_compat.py`
  - `docker/Dockerfile.vpn`
- **التعديلات الهندسية المطلوبة:**
  1. تشفير ملفات الكوكيز في `data/cookies/` باستخدام مفتاح بيئي مشتق من مسار نظامي آمن.
  2. إلغاء تخطي الفحص في `use_cache`، وإلزام النظام بإجراء استعلام خفيف لحالة الحساب الشخصي عند فتح كل جلسة لكشف الحظر والكابتشا مبكراً.
  3. تصحيح دالة `classify_x_account_failure` لتعتمد حصرياً على أكواد الخطأ الرقمية لـ X (`64`, `63`, `141`) وتجنب فحص النصوص الحرة الساذج.
  4. استبدال استعلام `api.ipify.org` المباشر بنقاط نهاية داخلية أو آمنة تفادياً لتسريب عنوان IP الخادم الحقيقي.
  5. إضافة حماية عند استيراد CSV لمنع استبدال الحسابات بملف فارغ.
- **معايير قبول المرحلة:**
  - ملفات الكوكيز مشفرة ولا تظهر نصوص المصادقة عند قراءتها المباشرة من القرص.
  - الحسابات المعلقة يتم اكتشافها فوراً عند الفتح وتُستبعد من دورة النشر.
  - عدم تسريب عنوان IP الخادم المضيف في أي طلبات شبكية.

---

### المرحلة 5: تحسين أداء محرك المحتوى والأتمتة (Content Engine Optimization)
- **الأولوية:** P1 / P2 (تحسين أداء تطبيق Electron وجودة التغريدات).
- **الملفات المتأثرة:**
  - `dev/automation/contentEngine.js`
  - `dev/automation/semanticIndex.js`
- **التعديلات الهندسية المطلوبة:**
  1. نقل حسابات الفهرس الدلالي `SemanticIndex` بالكامل إلى خيط مستقل (`Worker Thread`) لتحرير حلقة الأحداث الرئيسية لواجهة المستخدم.
  2. معالجة تضارب ميزانية التوكنات، واستبدال معالج الـ Regex الساقط بمحلل JSON متين يتعامل مع المصفوفات غير المكتملة بأمان.
  3. إضافة التحقق الإلزامي من خواتيم الجمل وعلامات الترقيم في `validateTweet` لمنع قبول التغريدات المبتورة.
- **معايير قبول المرحلة:**
  - استجابة سلسة لواجهة Electron بنسبة 60 FPS أثناء توليد دفعات التغريدات الكبيرة.
  - انعدام تام لقبول أي تغريدات مبتورة أو مقطوعة الأطراف.

## 📋 مصفوفة الاعتماد النهائي للإصلاح (Sign-Off Matrix)

| المرحلة | الفاحص المستقل | البيئة المطلوبة | متطلب النقل إلى الإنتاج |
|---|---|---|---|
| **Phase 1 (Publishing)** | محاكاة معزولة مغلقة شبكياً | Loopback HTTP Sandbox | 0 تكرار في كافة اختبارات انقطاع الاتصال |
| **Phase 2 (Telegram)** | بيئة النظام الفعلية | Isolated Systemd Multi-Process | قفل حصري موثوق وعدم تكرار 409 |
| **Phase 3 (SQLite)** | بيئة اختبار الأحمال | Torture Test (1000 items) | اجتياز اختبارات التزامن وانخفاض زمن الاستجابة |
| **Phase 4 (Security)** | فحص أمني جنائي | Local Security Audit | تشفير كامل للكوكيز ومنع تسريب IP |
| **Phase 5 (Content)** | فحص جودة وتجربة مستخدم | Desktop Automation Test | انعدام تجميد الخيط الرئيسي وضمان اكتمال النصوص |
