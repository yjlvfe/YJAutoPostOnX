## 👤 دورة حياة الحسابات وملفات الكوكيز

يدعم مشروع **YJAutoPostOnX** تشغيل ما يصل إلى 5 حسابات متزامنة نشطة (مع إمكانية تخزين حتى 1000 حساب في السجل العام).
تتم المصادقة على منصة X حصرياً عبر **جلسات الكوكيز المحفوظة مسبقاً (Session Cookies)** المستخرجة من المتصفحات، وتحديداً قيم `auth_token` و `ct0` (CSRF token) و `twid` (المعرف الرقمي).

### هيكل تخزين الكوكيز:
- يتم حفظ ملفات الكوكيز في المسار: `Bot/data/cookies/{accountId}.json` (أو صيغة Netscape/Text).
- يقوم الموديول `src/cookieFormat.js` بالتعرف التلقائي على الصيغة، واستخراج المفاتيح الإلزامية، وتنظيف الترويسات الزائدة.

## 🚨 المخاطر الأمنية والعيوب البرمجية في إدارة الحسابات

### 1. تخزين الكوكيز بنصوص صريحة دون تشفير (Plaintext Cookies Storage)
- **الملاحظة (OC-AUDIT-0004):** تُحفظ جلسات المصادقة الحساسة كملفات نصية صريحة (Plaintext JSON/Text) على نظام الملفات داخل `Bot/data/cookies/`.
- **الخطر الأمني:** رغم تطبيق صلاحيات `0600` على مستوى الملف، فإن أي اختراق محلي أو تسريب لمجلد البيانات يمنح المهاجم وصولاً دائماً وكاملاً لحسابات X دون الحاجة لكلمات المرور أو التحقق الثنائي (2FA).

### 2. تجاوز فحص الحظر والتعليق عبر `use_cache` (Bypassing State Checks)
في `src/directX.js:83-88`:
```javascript
const effectiveUserId = selected.userId || extractTwidUserId(resolvedCookie);
const result = await this._command(state, { op: 'open', account: {
  id: String(selected.id), username: expected(selected), userId: effectiveUserId,
  cookieFile: resolvedCookie,
  use_cache: Boolean(effectiveUserId && !selected.verifyNetwork),
}, proxy }, { timeout: this.openTimeoutMs, signal });
```
- **الخلل الجذري (HERMES-AUDIT-0002 / OC-SOLO-0006):**
  - يقوم الكود باستخراج المعرف الرقمي `twid` من ملف الكوكيز أو من قاعدة البيانات.
  - إذا وجد المعرف، يرسل أمر الفتح مع `use_cache: true`.
  - داخل `direct_x_bridge.py`، وجود `use_cache: true` يتخطى طلب فحص حالة المستخدم (`verify_credentials` أو استعلام الملف الشخصي عبر الشبكة الحية).
  - **الأثر الكارثي:** إذا تعرض الحساب للتعليق (Suspension) أو طُلب منه التحقق بالكابتشا (Arkose Challenge) أثناء عمل البوت، يستمر النظام في اعتبار الحساب صالحاً ونشطاً، ويوجه منشورات الطابور إليه، مما يتسبب في فشل النشر وتراكم المنشورات غير المحسومة.

### 3. الفحص الساذج للنصوص في تصنيف الأخطاء (Naive Substring Matching)
في `Bot/python/direct_x_compat.py:105-108`:
```python
combined = ' '.join(messages).lower()
if codes & {64, 63, 141} or 'suspended' in combined or 'banned' in combined:
    return 'banned'
```
- **الخلل الجذري (HERMES-AUDIT-0021):**
  - الكود يبحث عن كلمة `'suspended'` أو `'banned'` كجزء من أي نص خطأ قادم من واجهة X.
  - إذا تضمن نص التغريدة المراد نشرها، أو رسالة الخطأ العامة، أو اسم مستخدم، كلمة مثل "unsuspended" أو عبارة تفيد بحظر كلمة معينة في المحتوى، يُصنف الحساب بالكامل على أنه `banned`!
  - يتم إيقاف الحساب فوراً وتغيير حالته إلى "محظور" في واجهة المستخدم، بينما الحساب في الواقع سليم تماماً والخطأ كان في نص التغريدة أو قيود المحتوى.

### 4. خطر المسح العرضي عند استيراد CSV فارغ (Destructive Overwrite in /accounts_csv)
- في `src/runner.js` و `src/accounts.js`: واجهة تحميل ملفات الحسابات عبر تيليجرام تقبل ملفات CSV وتستبدل القائمة الحالية دون التحقق من احتواء الملف على حساب واحد صالح على الأقل.
- إرسال ملف CSV فارغ أو تالف يؤدي إلى حذف الحسابات النشطة الحالية فوراً.

## 🌐 البنية التحتية للشبكة وحاويات Docker SOCKS5

يعتمد عزل الاتصال لكل حساب على بنية تحتية محلية تتألف من 5 حاويات Docker:

```
الحساب 1 ──► SOCKS5h: 127.0.0.1:18801 ──► [yj_autopost_vpn_1] ──► NordVPN IP (خادم 1)
الحساب 2 ──► SOCKS5h: 127.0.0.1:18802 ──► [yj_autopost_vpn_2] ──► NordVPN IP (خادم 2)
الحساب 3 ──► SOCKS5h: 127.0.0.1:18803 ──► [yj_autopost_vpn_3] ──► NordVPN IP (خادم 3)
الحساب 4 ──► SOCKS5h: 127.0.0.1:18804 ──► [yj_autopost_vpn_4] ──► NordVPN IP (خادم 4)
الحساب 5 ──► SOCKS5h: 127.0.0.1:18805 ──► [yj_autopost_vpn_5] ──► NordVPN IP (خادم 5)
```

### معايير العقد والتشغيل (`src/dockerVpn.js`):
- اسم الحاويات: `yj_autopost_vpn_1` إلى `yj_autopost_vpn_5`.
- المنافذ المحلية: `18801` إلى `18805` بروتوكول SOCKS5 مع دعم حل الأسماء عبر الوكيل (`SOCKS5h`).
- وسوم الأمان: `io.yj-autopost.owner=yj-autopost` و `io.yj-autopost.contract=independent-v1`.
- ملف التوكن: يتم تحميل توكن NordVPN من ملف حصري مقفل الصلاحيات (`0600`) عبر `/run/secrets/nordvpn_token`.

## ⚠️ ثغرات الشبكة وحاويات البروكسي

### 1. الاعتماد على خدمة خارجية عامة (`api.ipify.org`) في فحص الاتصال
في `src/dockerVpn.js:68-80`:
```javascript
const { stdout } = await command('curl', ['--noproxy', '', '--socks5-hostname', `127.0.0.1:${port}`,
  '--ipv4', '--fail', '--max-time', '10', '--silent', 'https://api.ipify.org'], { timeout: 12_000 });
```
- **المشكلة (HERMES-AUDIT-0023):**
  - يتم استعلام خدمة `ipify.org` بشكل متكرر عند كل فحص دوري للحاويات.
  - إذا حظرت الخدمة عنوان IP أو توقفت، يفشل فحص الحاوية وتُعتبر معطلة رغم أن اتصال VPN سليم.
  - في دالة `getServerIp()`، يتم استعلام الخدمة بدون بروكسي (`--noproxy '*'`)، مما يسرب عنوان IP الحقيقي للخادم الرئيسي المضيف بانتظام.

### 2. غياب زر الفصل القاطع الفوري (Kill-Switch Gap)
- **الملاحظة (OC-SOLO-0007):**
  - يتم فحص حالة البروكسي قبل إطلاق الجلسة (Pre-flight Check).
  - لكن في حال انهيار اتصال VPN أثناء محاولة النشر (بين فتح الجلسة وإرسال بايتات HTTP)، لا توجد آلية تمنع تسرب الاتصال المباشر إذا كان التوجيه يسمح بذلك، مما يعرض أمان الحساب للارتباط بعنوان IP الخادم الحقيقي.
  - *تخفيف الأثر الحالي:* يفرض `direct_x_bridge.py` استخدام `socks5h://` قسرياً، وبالتالي يفشل الطلب بانقطاع الاتصال بدلاً من التسرب، لكن يجب تعزيز ذلك بقواعد جدار ناري محلية (iptables kill-switch).

### 3. تباعد طبقات صور الحاويات (Divergent Image Layers)
- لوحظ في التدقيق وجود حاويات تم بناؤها بتواريخ متباعدة دون تثبيت رقم الإصدار الدقيق لحزمة NordVPN داخل `Dockerfile.vpn`، مما يؤدي إلى تفاوت في إصدارات العميل وسلوك إعادة الاتصال التلقائي بين المنافذ المختلفة.

## 🛡️ الإجراءات التصحيحية الموصى بها
1. **تشفير ملفات الكوكيز:** استخدام تشفير AES-256-GCM لمجلد الكوكيز بالاعتماد على مفتاح محلي مشتق من بيئة الخادم.
2. **إلغاء التخطي التلقائي في `use_cache`:** إلزام النظام بفحص شبكي حقيقي سريع لحالة الحساب (User Profile Status) عند فتح أي جلسة قبل بدء النشر.
3. **تصحيح تصنيف الأخطاء:** حصر فحص الحظر بالأكواد الرقمية الصريحة (`64`, `63`, `141`) أو نصوص الأخطاء المهيكلة من كائنات JSON فقط مع تجنب مطابقة النصوص العامة.
4. **استبدال فحص IP بخوادم داخلية أو موثوقة:** تجنب إرسال طلبات مجردة إلى `ipify.org` واستخدام نقاط نهاية موثوقة أو متعددة مع تفادي تسريب IP الخادم.
